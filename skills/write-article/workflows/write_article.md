# 公众号文章生产工作流 (Official 5-Step Workflow)

这是一个强制性的工作流。所有通过 `/write`、`/article` 或任何“写文章”请求触发的任务，**必须严格**遵循此流程。

流程核心逻辑：**5次选择，步步确认**。严禁 AI 自作主张跳过任何确认环节。

---

## Step 1: 热点扫描与评分 (Discovery & Scoring)
**触发条件**：用户未提供明确主题，或要求“看最近的新闻/找灵感”。

**动作**：
1. **智能工具选择（强力推荐）**：
   - **优先检测**：检查是否可用主 `tavily_search` (MCP)。
   - **执行策略**：
     - 若有 `tavily_search` -> **必须优先使用**它执行所有搜索任务（它在 AI 垂直领域更精准）。
     - 若当前 Tavily 返回套餐额度耗尽、限流或认证错误 -> 保持相同参数，依次自动改用 `tavily_backup`、`tavily_3`、`tavily_4`、`tavily_5`、`tavily_6` 的对应工具。
     - 六个 Tavily 入口均不可用 -> 降级使用 `search_web`。

2. **三轨搜索机制**：
   - **轨道1（公域热点）**：搜索 AI 科技新闻、GitHub Trending、Hacker News、Reddit (r/LocalLLaMA)。
   - **轨道2（私域关注 - 强制）**：**必须专项搜索** Moltbot (OpenClaw/Moltbook)、DeepSeek、Agent 落地案例、用户自建项目。
   - **轨道3（AI 世界观察 - 强制）**：专项搜索全球 AI 采用、工作与就业、组织变化、投资与商业、政策治理、信任安全、算力能源等报告和持续数据。优先使用 McKinsey、Stanford HAI、PwC、Microsoft Work Trend Index、WEF、OECD、IMF、IEA、ILO、Anthropic Economic Index 等机构的一手报告或官方数据页，不拿二手媒体摘要代替原始来源。
   - 每轮 10 个候选中，**至少 2 个来自轨道3**。每个报告型候选必须补齐：发布日期、原始报告 URL、至少 1 个可核实的关键数据、它会怎样影响目标读者的工作/成本/风险/职业判断。
   - 报告超过 7 天不等于不能写：先进入存稿池；找到 7 天内的新事件、新数据或现实案例重新激活后，再升级为当期选题。严禁把旧报告包装成刚发布的新闻。

3. **选题价值过滤（强制，2026-08 修订）**：
   每个候选热点必须标注三个属性。"时效在窗口内 × 与目标读者有关 × 我能提供可靠增量"的**交集**才是首选选题：
   - **时效性（三级，不搞一刀切）**：
     * **爆发期（48h 内）**：突发事件/产品发布，直接追，优先级最高。
     * **发酵期（3~7 天）**：仍有新增讨论、二次事件或**中文信息差**（海外热议但中文圈还没讲透）的选题，可以写，但角度必须带增量，不能当新闻转述。
     * **存稿池（热度已退）**：只保存**选题线索**（方向+核心事实+来源），**不是成稿换标题重发**；等新事件重新激活时，必须重新搜索、重新核实、补充新增量后再写。
   - **目标读者关联**：它会不会改变目标读者的工作方法、成本、风险、产品判断或商业选择？只热闹、与这些都无关的，标注 ⚠️。
   - **价值来源**：这篇能靠哪一种增量成立——亲自实测 / 核一手信源 / 拆成本与边界 / 系统分析 / 产品实践思考？至少明确一种。观点和启发可以单独成立；只有空泛感想、没有事实支点或新判断的，标注 ⚠️。
   *依据：高阅读文章多在热点窗口内，并带清晰的动作、信息差或读者收益（这条来自实际发布数据复盘，建议你也建一份自己的台账验证）。这套过滤筛的是“受众一眼可识别、推荐流相对友好且有内容增量”的选题，不等于保证被推荐，也不等于每篇都要亲测。*

4. **标准化输出格式（强制）**：
   整理并罗列 **10 个大热点**，分为五个分组。每条包含：**标题** + **评分(1-10)** + **时效标注(爆发/发酵/存稿)** + **目标读者关联** + **价值来源/写法** + **一句话犀利点评**。
   *评分标准：传播潜力、认知冲击、话题争议性（9-10分=现象级 | 7-8分=圈内刷屏 | 5-6分=干货）。*

   **输出模板**：
   ```text
   ### 🔥 私域必看
   *（此处优先放 Moltbot/DeepSeek/Agent落地 等私域关注内容）*
   1. **[标题]** ([评分]/10)
      *时效：[爆发/发酵/存稿]｜目标读者关联：[工作/成本/风险/产品判断/商业选择]*
      *价值来源：[亲测/一手信源/成本与边界/系统分析/产品实践思考]*
      *[一句话点评：核心看点、矛盾或读者收益]*
   ...

   ### 🌐 AI 世界观察
   *（每轮至少 2 条；报告型候选补发布日期、原始报告 URL、关键数据和读者影响）*
   ...

   ### 🌍 全球热点
   ...

   ### 🇨🇳 国内动态
   ...

   ### 🔬 技术前沿
   ...
   ```

5. **强制检查点 (CheckPoint 1)**：
   - **必须停止**，等待用户从 10 个热点中**选择 1 个**感兴趣的方向。

---

## Step 2: 深度选题角度挖掘 (Angle Mining)
**触发条件**：用户完成了 CheckPoint 1，选定了一个热点。

**动作**：
1. **深度发散搜索**：优先使用主 `tavily_search` (MCP) 针对该热点进行深度背景调研（技术原理、社会影响、争议点）。如果当前服务返回套餐额度耗尽、限流或认证错误，保持相同参数，依次自动改用 `tavily_backup`、`tavily_3`、`tavily_4`、`tavily_5`、`tavily_6` 的对应工具；六个入口全部不可用时才使用 `search_web`。
2. **深度思考挖掘 (Critical Thinking)**：
   - **强制事实核查 (Show the Receipts)**：在挖掘前，必须亲自通过工具核实该热点的核心数据、事件或出处。**如果没有找到至少一个你能亲自验证的第一手细节（如原始推文、财报原图、权威报道原文），必须拒绝该方向重新选择。** 不要在虚假的地基上建楼。
   - **必须**调用 `sequentialthinking` 工具。
   - 设定思考目标：“分析该热点的关键机制、二阶效应，以及它会怎样改变目标读者的工作、成本、风险或判断”。
   - 至少进行 3-5 步深度推演，拒绝表面资讯堆砌。
3. **多维角度挖掘**：
   基于思考结果，挖掘 **10 个不同的选题切入角度**。

   **输出格式要求（强制）**：
   每条选题必须包含以下评分指标（1-10分）：
   - **🔥 传播性 (Spreadability)**：大众吃瓜/情绪共鸣程度
   - **🛠️ 实用性 (Utility)**：落地实操/复用价值
   - **🧠 专业度 (Depth)**：认知深度/行业洞察

   *角度参考示例：*
   - *技术原理角度（它是怎么实现的？） [🔥6 | 🛠️8 | 🧠9]*
   - *社会/伦理角度（人类要被替代了吗？） [🔥9 | 🛠️2 | 🧠7]*
   - *实操避坑（千万别这么用...） [🔥7 | 🛠️10 | 🧠5]*

4. **强制检查点 (CheckPoint 2)**：
   - **必须停止**，展示 10 个角度，等待用户**选择 1 个**切入点。

---

## Step 3: 车道适配建议 (Lane Consultant)
**触发条件**：用户完成了 CheckPoint 2，选定了一个角度。

**动作**：
1. **车道匹配分析**：
   分析用户选定的角度更适合哪条写作车道：
   - **车道 A（传播解读流）**：适合有热点入口、需要靠传播机制拿点击和转发的选题；写法上会死磕一个最离谱的细节。不要求每篇亲测。
   - **车道 B（实操干货流）**：适合真实工具测试、工作流、模板和避坑教程，重点是收藏、复用与长尾价值；选择这条车道才强制真实实测。
   - **车道 C（观察思考流）**：适合资讯解读、报告拆解、趋势判断和观点评论——凡是"从一个公共事实出发，讲清为什么会这样，给读者留一把能复用的尺子"的选题都走这条。不要求亲测，但必须交付一个可复用的判据 + 一个可被反驳的判断。**这是本号解读型稿件的主力车道**，不要再用车道 A 的爆文壳硬套。

2. **顾问建议输出**：
   - 给出 **星级评分**（例如：车道C ⭐⭐⭐⭐⭐ vs 车道A ⭐⭐⭐ vs 车道B ⭐⭐）。
   - **判断口径**：素材核心是"我测了/我做了" → B；有强热点入口且靠一个离谱细节撑全场 → A；核心是"我怎么看这件事、从中提炼出什么判断" → C。三选一拿不准时默认 C（本号解读稿占比最高）。
   - 用产品经理能懂的语言阐述**推荐理由**。

3. **强制检查点 (CheckPoint 3)**：
   - **必须停止**，等待用户回复选择 **"A"**、**"B"** 或 **"C"**。

## Step 4: 标题生成 (Headlines)
**触发条件**：用户完成了 CheckPoint 3，选定了车道。

**动作**：
1. **读取规则**：
   - 车道 A -> 读取 `skills/write-article/lanes/车道A.md`
   - 车道 B -> 读取 `skills/write-article/lanes/车道B.md`
2. **生成标题**：
   根据 Prompt 中的标题公式，结合 Step 2 选定的“角度”，生成 **10 个备选标题**。
   - **(Skill 增强)**: 必须加载 `copywriting` Skill (`skills/copywriting/SKILL.md`)，使用其中的 "High Conversion Formulas" 优化标题，确保点击率。
   - **标题配比硬规则（强制，2026-08 修订）**：先按文章类型分流，再生成 10 个候选：
     * **热点/事件型**：≥3 个含 7 天内热词（产品名/模型名/名人/机构/事件名，受众一眼可识别、推荐流相对友好）；**常青产品复盘/观点型不设热词配额**，改为 ≥3 个含具体工作场景、产品对象或真实矛盾；
     * **实测/解读型**：≥3 个含“我 + 真实动作 + 反常结果”（如“我把 X 翻完了/跑了一遍，结果……”）；
     * **产品复盘/观点型**：不强求“我+动作”，≥3 个要写出“具体矛盾/真实处境 + 清晰判断”，让读者知道这篇会帮他重新理解什么；
     * **纯判断句/纯结论句标题（如"A 不等于 B""X 反而更难了"）最多保留 2 个陪跑，默认不作推荐首选**（例外：用户明确表示本篇是养人设的判断文时，可由用户指定判断句标题）。
     * 向用户展示时标注每个标题命中哪类（🏷️热词 / 🙋真实动作 / 💡思考判断 / ⚖️纯判断句），默认推荐“主体可识别 + 收益或矛盾具体 + 正文证据能兑现”的标题。
     * *依据：历史数据中热词或第一人称动作更利于推荐流分发（同样来自发布数据复盘，你的号可能不同，以自己台账为准）。这条用于优化传播入口，只能说明空泛判断句标题风险较高，不能否定有具体矛盾支撑的产品思考和观点文章。*
   - **"我+动作"真实性护栏（红线，与 persona 反预测原则同源）**：只有**用户素材或实际调研记录能证明"确实做过"**时，才允许生成"我测了/我跑了 N 次/我用了 N 天"类标题；**严禁为标题吸引力虚构体验、时长、次数或情绪**。AI 替用户翻了资料 ≠ 用户本人做过。素材撑不起"我测了"的，改用"我翻完了原文/我把 X 拆了"这类查证型动作（查证也必须真的做了）。
   - **首选前三问（终选校验，配比是地板、三问是门槛）**：默认推荐的那个标题必须同时过——① 主体一眼可识别吗（不认识的人名/黑话不上标题）？② 收益或风险具体吗（读者知道点进来能拿到什么）？③ 忠于正文证据吗（标题承诺的正文兑现得了，不比正文更满）？任何一问不过，换标题。

3. **强制检查点 (CheckPoint 4)**：
   - **必须停止**，展示 10 个标题，等待用户**选择 1 个**（或要求优化）。

## Step 4.5: 模块数量自动决策 (Auto Module Count - 全自动)
**触发条件**：用户确认标题后，**自动执行，不询问用户**。

**动作**：
1. **智能分析内容类型**：
   回顾 Step 2 选定的"角度"和 Step 1 的"热点"，判断内容属于：
   - **单一逻辑链**（A→B→C推导关系）
   - **并列观点组**（2-3个独立观点）
   - **盘点式现象**（多个独立信息点）

2. **自动选择模块数**（参照 `skills/write-article/lanes/车道A.md`「模块数量自动决策」一节）：
   - ✅ **3个模块**：深度单一逻辑链
   - ✅ **4-5个模块**：标准叙事或并列观点
   - ✅ **6个模块**：盘点式、碎片化信息

3. **静默执行**：
   - **不需要用户确认**。
   - 在正文撰写时严格按照自动选定的模块数撰写。
   - （可选）在输出时简要说明："✓ 根据内容类型，自动使用X个模块结构。"

## Step 5: 正文撰写 (Writing)
**触发条件**：用户完成了 CheckPoint 4，确认了标题。

**动作**：
0. **人味盘点（写作前强制，按文章类型分级，见 persona.md「五、语义层人味」）**：
   - **先判断文章类型**：实测/经历型、资讯解读型、产品复盘/实践思考型、观点评论型。
   - **实测/经历型**：必须有 ≥3 条真实私货细节（日期/次数/金额/对话/翻车现场）。用户素材里没有 → 中断询问；用户也给不出 → **降级为解读型来写**，把"我测了"改成"我看了/我翻了"，严禁编造亲历。
   - **资讯解读型**：不强制亲历细节，但必须列出 ≥2 处独立判断（哪里不同意原文/什么信息没讲/怎么翻译成目标读者可用于工作和决策的信息）。
   - **产品复盘/实践思考型**：不强制教程、完整测试数据或“我测了”式动作，但必须有 ≥1 个来自真实工作或产品实践的具体矛盾/观察，以及 ≥1 个可被反驳的判断。素材不足就向用户索取，严禁补写不存在的经历。
   - **观点评论型**：不强制亲历细节，但必须有 ≥1 个事实或案例支点，以及 ≥1 个可被反驳的立场判断。
   - **通用**：每篇至少明确一种价值来源（亲测 / 一手信源 / 成本与边界 / 系统分析 / 产品实践思考）。私货只能来自用户素材；没有亲测就按对应类型写，绝不虚构。

1. **执行撰写**：
   - **(底味加载 — 最高优先级)**: 确保**已加载** `skills/write-article/rules/persona.md` 全局规则，将其中的角色定义、词汇黑名单、风格案例、**「五、语义层人味-反预测原则」**作为最高优先级约束。车道 Prompt 管「结构」，persona.md 管「味道」，两者必须叠加。
   - 严格按照对应车道 Prompt 中的结构（如“30秒兑现”、“短视频结构”）撰写正文。
   - **(Skill 增强)**: 撰写过程中，必须实时应用 `humanizer-zh` Skill (`skills/humanizer-zh/SKILL.md`)，强制去除所有 AI 味（如“综上所述”、“本质上”），确保文本像“真人聊天”。
   - **(关键)** 遇到图片建议或引用关键数据/案例时，**必须**调用 `tavily_search` 或 `search_web` 找到真实的素材来源链接。**在正文中引用处必须直接附带该 URL**，以便用户能直接跳转截图。严禁只留空或放到文末。
   - **(段落配图-四类分工)**: 写正文时 **AI 主动判断**哪些段落需要配图、配哪类图（**数字/数据对比/流程/结构/概念示意 → ④（首选）**，需插画感/人物场景的概念图 → ①，引用外部页面 → ②，工具实操 → ③），配图紧跟在段落**后面**，正文用 `![说明](images/<文件名>.png)` 引用（详细规则见车道A/B的「段落配图」条款）。四类处理方式：**① AI 生成图**只交付 prompt 到 `prompts/`（与图片同名），prompt 按 **ChatGPT 图像生成（img2）** 的出图习惯写（自然语言描述+比例+图内文字逐字写明），不自动生成图片，**图内严禁放大标题/副标题/来源注释/底部标语**（正文已有，配图只做内容图形化或补充，只留图形必需的元素标签，详见车道A/B「图内文案禁令」）；**② 网页/来源截图**由 AI 实际截图存入 `images/`（**X 推文截图必须用 `skills/twitter-capture/` 的公开嵌入接口法**：无需登录，`python3 skills/twitter-capture/capture_tweet.py <推文ID> <输出.png> [--hide-media]`，评论类加 `--hide-media` 控制高度，一处一张严禁多条拼长图），确实截不了就在 `sources.md` 写明 URL+截图位置+建议文件名；**③ 用户实操界面图**由 AI 输出专门文件 `output/[article-slug]/需亲手实测.md`（不再散落在 sources.md），每张图一节，必须包含：a) 可直接复制的测试命令/操作路径；b) 截图取景要求——**触发动作（命令行/按钮/输入）与关键结果必须同框**，注明哪些元素必须露出、后续内容可裁边；c) 目标文件名（与正文引用一致）；d) 一句"读者视角"说明——这张图不要求读者看懂内容，只要求目击什么（写配文时照此解压）。用户截好放入 `images/` 后由 AI 插入正文并重转 HTML;**用户在聊天中粘贴的截图,AI 必须当场复制归档**(原图进 `notes/`、裁边版进 `images/`),聊天图片缓存会失效,失效即证据灭失。判定口径：**需要用户登录态/本机环境/付费额度的操作界面 → ③；公开网页上的信息、评论、帖子 → ②（AI 直接截）**；**④ 代码生成数据/逻辑图**由 AI 用 **matplotlib 直接出图**存入 `images/`（画图脚本存 `prompts/<同名>.py`，非 .md），**必须遵守统一视觉规范** `skills/house-style/references/matplotlib-chart-style.md`（米白底+墨+橙、中文字体必设 PingFang SC、图内文案禁令照旧），封面/海报/人物插画不走 ④ 回 ①。
   - **(出图默认)**: 当用户**明确要求生成**封面图、海报、信息卡等图片时，默认使用 **Codex 内置出图能力**（正文段落配图①类默认只交付 prompt，不主动出图）。不要默认调用 Google/Gemini/DashScope 等外部图片 API，也不要默认使用 `baoyu-image-gen` 的 Google/DashScope provider。可以借用 `baoyu-cover-image`、`baoyu-infographic`、`baoyu-slide-deck` 的 prompt 结构、画风规则和版式规则，但只作为 Codex 内置出图的 prompt 设计依据。只有用户明确指定外部 provider 或 Codex 内置出图无法满足时，才说明原因并等待用户确认。

2. **输出文件格式要求（强制）**：
   - 先为文章创建一个英文 slug 命名的专属文件夹：`output/[article-slug]/`。
   - 正文文件保存为：`output/[article-slug]/[article-slug].md`。
   - **严禁**把新文章正文直接保存为 `output/[article-slug].md`。
   - **文件开头必须包含：** `## 标题备选`（罗列之前的 10 个标题）。**这一节只放 10 条标题本身，不要加任何说明行、配比统计、注释**——`convert_to_wechat.py` 只把标题列表收进隐藏 div，列表外的独立段落会**漏进正文 HTML**，读者能看见。（2026-07-31 workbuddy 稿实际踩到：加的「🏷️热词 5 个 / 🙋我+动作 5 个」统计行原样出现在正文顶部。）
   - **紧接着是：** `## 正文成稿`。
   - **后续模块必须包含：** `## 写在最后`、`## 可转发金句`。
   - **中文标点（强制，`check_article.py` 第 4 组已自动拦截）**：正文一律用**中文弯引号 “ ”**，严禁英文直引号 `"`（转微信后直引号显示成一撇竖线，很扎眼）。冒号、逗号、括号同理一律用中文全角。**例外**：代码块与行内代码里保持原样（那是代码）。

4. **可转发金句与自然收束**：
   - `## 可转发金句` 只保留文字，不强制生成金句图卡。
   - `## 写在最后` 回到作者自己的动作、判断或仍未解决的问题，自然收住。
   - 禁止固定追加点赞、在看、关注、转发等互动话术，也不要向读者解释公众号推荐机制。
   - 只有文章确实提供配套资源、系列续篇或服务，而且用户明确要求时，才添加与内容直接相关的说明。

3. **文章文件夹资产管理规则（强制）**：
   - 每篇文章只能使用自己的专属目录：`output/[article-slug]/`。
   - **所有与该文章相关的文件**都必须保存在这个目录里，包括正文、封面图、配图、截图、prompt、调研链接、资料摘录和临时笔记。
   - 图片统一保存到：`output/[article-slug]/images/`。
   - 每张图片的生成 prompt 必须保存为同名 `.md` 文件，统一放到：`output/[article-slug]/prompts/`。
     例如：`images/cover.png` 对应 `prompts/cover.md`。
   - 如果使用 Codex 内置出图暂时只能直接返回图片，也必须先把最终 prompt 保存到 `prompts/` 目录；拿到可保存图片后再放入 `images/`。
   - 调研资料、关键来源链接、截图说明保存到：`output/[article-slug]/sources.md`；较多临时材料可放入 `output/[article-slug]/notes/`。
   - **严禁**将新文章的正文、图片、prompt、资料直接散放在 `output/` 根目录下。
   - 文件夹结构示例：
     ```
     output/
     └── claude-code-leak/
         ├── claude-code-leak.md      # 文章正文
         ├── sources.md               # 调研资料、来源链接、截图说明
         ├── 需亲手实测.md             # ③类图专用：给用户的实测步骤+截图取景清单（有③类图时必建）
         ├── images/
         │   ├── cover.png            # 封面图
         │   └── 01-illustration.png  # 文内配图
         ├── prompts/
         │   ├── cover.md             # 封面图 prompt
         │   └── 01-illustration.md   # 文内配图 prompt
         └── notes/                   # 可选：临时笔记、素材草稿
     ```

5. **缺口清单（成稿后立刻填，强制）**：
   - 写完正文的**第一件事**：在 `sources.md` 末尾追加一节 `## 缺口清单（成稿时填）`，逐条列出正文里**依据不满**的地方。三类：
     * `[推断]` 材料没这么说，是我从材料推出来的。
     * `[未核实]` 查了但没找到一手来源，或来源日期存疑。
     * `[建议]` 我的判断和主张，不是事实。
   - 每条格式：`- [类型] 位置（第几节 / 哪句话）— 一句话说明缺什么`。
   - **为什么强制**：写的时候「读着顺」和「有依据」是两种感觉，写完就分不清了。作者自己标缺口的成本接近零，漏标的成本是发出去被懂行的人抓。
   - **红线 1**：清单可以为空，但必须是**逐段过完之后**确认为空；不许因为「感觉都有依据」就跳过不写这一节。
   - **红线 2｜核缺口必须回原始 URL，不许回 `sources.md` 核**：调研记录是二次转述，本身就会漏记。拿它当尺子量正文，会把「记录漏了」误判成「正文错了」，凭空造出假缺口。（活教材：2026-07-31 用 sources.md 核 workbuddy 稿，两条「必须核」的疑点回原页面一查全是正文对的——sources.md 把定价页概括成"只列积分额度"，漏了它其实有整张基础/加赠拆分表和三档折扣。）顺带：核完发现记录有漏，**当场把 `sources.md` 补全**。
   - 这份清单是 Step 5.5 技术准确性审查和引用溯源检查的对照表。

## Step 5.5: 强制质检关卡 (Mandatory Quality Check - 自动化)
**触发条件**：Step 5 完成后，**自动触发**，不允许跳过。

**动作**：

0. **时效关（第一道，不过就别往下跑了）**：
   - **为什么必须放在最前**：时效过滤只写在 Step 1（选题），而选题到成稿之间只要拖过窗口期、或者选题本身就是存稿池里的旧料，**后面四关（结构 / AI 味 / 黑名单 / 合规）没有任何一关会拦**。等发出去才发现是旧闻，前面所有功夫全白做。（活教材：2026-07-31 的 workbuddy 稿，事实层和 AI 味全过，用户一句"太延时就没意义"直接打回——由头是 3 个月前的公告，开篇没有任何时间锚。）
   - **动作**：只看**读者读到的第一句时间信息**（不是正文里最新的那个数字，是开篇锚点）：
     * 锚点在 **14 天内** → 通过。
     * 锚点超期，但能找到一个**未来的确定事件**（截止日 / 生效日 / 发布日）→ 改挂它并重写开头。**未来锚点优于过去锚点**：读者有行动理由，且发布后仍在窗口内。改完**必须回头重跑盲预测测试**（开头变了，旧盲测作废）。
     * 两者都没有 → 退回 Step 1 重新选题，不许硬发。
   - **红线**：旧事件只能作为「标本 / 证据」出现在正文中段，且必须写明时间距离；**严禁把旧新闻摆在开头冒充新闻**。

1. **统一自检（一条命令，Tool Check）**：
   - **必须**运行 `python3 skills/write-article/scripts/check_article.py output/[article-slug]/[article-slug].md`
   - 该脚本按顺序执行 4 组检查，任何一组❌都会导致整体不通过（退出码 1）：
     * **[1/4] 结构与字数**（audit_article.py）：字数 ≥1000（车道A建议 1000-2500 / 车道B建议 2500-3000 / 车道C建议 2000-2800，>3000 仅提示）；写在最后/金句模块；第一人称 ≥3 次。数据来源不再单独列文末清单，正文引用处直接带 URL 即可
     * **[2/4] AI 味检测**（detect_ai_tone.py，13 项）：结构工整度/序列化痕迹/术语密度/外链真实性/情绪表达/网络梗密度/三连排比（顿号版+逗号版，逗号版带"结构重复"校验防误伤）/**三连短句连击**/**自我限权表态**/破折号密度/模糊归因/连接词密度/E类对比句式（"不是A，而是B"零容忍，扫全文含标题和金句）。**加粗两项为 2026-07-31 新增，对应 persona F 类「句式节奏工整」——外部模型两次独立指认「词汇干净但节奏工整过头」，脚本当时全报 0 分完全抓不到**；另输出🧬语义层提醒（私货细节≥3处、可被反驳观点≥1个），提醒不阻塞但必须报告用户
     * **[3/4] 词汇黑名单**：动态读取 `persona.md` A/B/C/D 类禁用词全文扫描（改黑名单只需改 persona.md，脚本自动生效）
     * **[4/4] 平台合规与引用溯源**：诱导关注/不正当引流话术、敏感表述（微信推荐流红线，命中即❌）；导流话术和"有数据无引用URL"给⚠️提醒
   - **如果退出码为 1**：自动进入修复模式（按脚本输出逐项修复），然后重新运行，直到通过。
   - **⚠️提醒项**：不阻塞通过，但必须在质检报告里向用户列出，由用户确认。

2. **软指标反思审核（AI Check）**：
   - **必须**调用 `sequentialthinking` 工具。
   - 设定角色为："苛刻的主编"。
   - 检查：文章是否有"AI味"、逻辑是否流畅、情绪是否到位。
   - **全文一致性核对（强制，通读全文靠理解做，不靠固定句式）**：把成稿从**标题、正文、图注、图内文字到金句**完整读一遍（图注/图内字/金句与正文**同权**，且因为更抢眼要审得**更严**），核对所有"承诺→兑现"关系，包括但不限于：
     * **结构变更回扫**：只要删掉、合并或改名了模板、清单、图片、数字项，必须立刻全文搜索它的旧名称，并回查所有汇总段（如“正文已经给全”“文中包含”“资源包”）、标题数字、图内文字和结尾复述。发现仍在承诺已删除内容，必须同步删除或改写；不得只检查刚改的局部。
     * 数字承诺：标题/正文说"N 个/N 件事/N 条"，实际内容数得出 N 个吗？用"第X个"编号的，从第一个到第 N 个链条完整吗？
     * 结构承诺：标题/开头预告了什么（坏消息/清单/对比/时间表），正文每一项都能对上号吗？
     * 受众一致：这篇是否始终写给“不靠写代码吃饭、但想把 AI 接进工作的人”？有没有混进只对开发者、投资人或平台商家成立的内容而没有解释关联？
     * 前后矛盾：数据、立场、称谓、案例细节前后打架的地方？
     * **图注/图内字/金句 ≤ 正文的分寸（强制）**：先在心里立一张"事实总账"——把关键数字、分寸词（有时/约/大概/仅/拒绝/往往）、定性结论列出来；再逐个位置对表。同一个事实在标题、正文、图注、图内文字、金句里**必须一致，且任何一处都不许比正文更满、更绝对**。图注/金句/图内字是读者扫文最先记住的，最松的话绝不能写在最显眼处。（活教材：正文写"约 7% 会要挟"，图注却写"就去要挟"、图里写"这才是真面目"——把 7% 写成了 100%，还把"拒绝"诛心成"装正义"。）
   - 任何一处对不上 → 修正后重新核对。这类错误（如"标题三件事、列表四条""图注比正文满"）曾多次被人工/外部模型抓到，机器正则抓不全，只能靠通读。
   - **语义层盲预测测试（强制，替代"自己判断有没有 AI 味"）**：
     - **为什么不许自答**：persona.md 的标准是「让另一个 AI 续写它绝对编不出来的句子」。**这题自己答不了**——我知道自己写了什么，所以永远会觉得"它编不出来"。这不是容易漏，是逻辑上不成立，必须换一个不知情的上下文实测。
     - **动作**：起一个**干净的子 Agent**（不给成稿、不给调研材料、不给写作过程），只给三样：① 一句话选题；② 最终标题；③ 正文前两段。要求它**按这个标题往下续写 400-600 字**。（此项已由用户授权在写作流程中调用 Agent 工具，不必每篇再问。）
     - **⚠️ 选题那句只许写「写什么对象 / 什么事件」，严禁写进本文的结论或核心论点**——否则等于把答案喂给它，它复述回来会被误判成"撞车"，结果偏严。（活教材：workbuddy 稿三轮盲测的选题句里都带了"官方没公开换算规则"这个结论，第三轮唯一那处撞车正是它复述这句，属自造的假撞车。）
     - **比对判定（关键：分清撞的是什么）**：
       * ❌ **撞在论证角度、段落骨架、核心类比、举例方式上** → 真问题。说明这部分是模型的默认输出，撞上的段落**必须换角度重写**。
       * ✅ **它没写到我的独家事实/数字/亲历细节** → **不算加分**。那是"有没有一手材料"（Step 2 已管），不是"有没有人味"。严禁拿这条自我安慰过关。
     - **成本控制**：只喂开头，不喂全文；每篇一次，重写后可再测一次。
   - **另两问（可自答，必答）**：
     1. 把所有金句删掉之后，这篇还剩下一个真观点吗？
     2. 熟人读完能不能看出"这确实是作者写的，不是 AI 写的"？
   - 盲测撞车或任何一问答"否" → 回 Step 5 补私货/补观点/换角度，不许硬发。

3. **技术准确性审查（技术/科普/解读类文章强制，AI Check）**：
   - **为什么单设这关**：上面所有检查（脚本 + 主编审稿）查的是「味道 / 结构 / 合规 / 逻辑顺不顺」，**没有一关查「技术说得对不对」**。AI 写科普最典型的翻车是「读着顺、细节经不起懂行推敲」的过度简化——比喻越通俗，越容易在关键机制上失真。这类错误自查抓不住（写的时候会觉得「顺 = 对」），必须换一个专门抬杠的视角重审。词汇黑名单、AI 味脚本都拦不住它，因为它不是味道问题，是事实问题。
   - **触发条件**：文章只要涉及技术机制、原理解释、技术类比、性能数据（科普型、技术解读型基本都算）。判断不了就默认触发。
   - **动作**：
     1. **强制切换视角**：把自己当成「一个会抬杠的领域专家」，假设读者里就坐着一个懂行的人，专门来找茬。
     2. **逐条过技术表述（含图注、图内文字、金句，不只正文散文——图注/图内字是二次生成、最容易脱离核查语境写得比正文满，必须一并过这道关，并回原始信源核数字与分寸词）**，重点盯这几类高危处：
        - **每一个类比 / 比喻**：这个比喻在真实机制上站得住吗？为了顺，牺牲了哪个关键细节？牺牲得起吗？
        - **绝对化措辞**（每次 / 所有 / 一定 / 完全 / 从头 / 必然 / 根本不）：真的绝对吗？有没有被忽略的缓存、优化、例外、边界条件？（历史翻车点：写「每写一个字都从头重算一遍」，漏了 KV Cache——现代推理并不重算前文，真正瓶颈是串行依赖 + 内存带宽）
        - **因果方向**：A 导致 B，会不会说反成 B 导致 A？
        - **数据口径**：百分比的分母、对比基线、适用范围说清了吗？
     3. **优先用工具二次核实**，别凭记忆下判断：拿不准的技术点，用 `tavily_search` 查官方文档 / 论文原文 / 权威解释，核对后再定。
     4. **输出**：列出每处技术表述的判定（✅准确 / ⚠️过度简化 / ❌错误）+ 修正建议，报给用户。
   - **红线**：宁可为严谨多啰嗦一句（如正文里直接补一句「免得懂行的挑刺，其实……」），也不留「顺滑但错误」的类比；拿不准又核不实的技术点，标注「[待核实]」交用户，严禁凭感觉硬写成肯定句。

4. **洗稿与原创性自查（凡「参考了某篇范文」必做，最高优先级）**：
   - **触发条件**：本次写作参考了用户提供的某篇文章 / 某个爆款范文（哪怕只是「参考着写一篇同主题的」）。
   - **为什么单设**：AI 会收敛到「看到的最优模板」，参考范文时极易从「参考」滑成「复制」，把它的骨架 / 比喻 / 金句搬过来。这是洗稿，是原创性红线，而词汇黑名单和 AI 味脚本都查不出来。
   - **动作**：把参考的范文调出来，与成稿**逐段比对**——开篇框架、论证顺序、每个比喻、每句金句、叙述节奏，有没有和它撞的（**神似也算，不只查字面逐字**）。撞一处改一处，用自己的角度重写。**再细查一层词句级**：范文里带个人色彩的特征词（某个动词/绰号/非标准译法）一律不许沿用；凡范文提过的事实，成稿措辞回**原始信源**核定直译，不跟范文（活教材：范文「会吐丝」vs Anthropic 原文「spins webs/结网」，一个词也算洗稿残留）。
   - **红线**：范文只提供「事实素材（自己回一手核）+ 选题方向」，其余一律自己重起框架。判定与正反案例见 `persona.md` 案例8。
   - **输出**：向用户报告「洗稿自查：已比对范文，无雷同 / 已改 N 处」。

5. **强制报告**：
   - 硬性+软性指标全部通过 → 输出："✅ 质检通过（字数X，模块Y，⚠️提醒项Z条，技术准确性审查：无硬伤 / 已修 N 处，洗稿自查：无雷同 / 已改 N 处）。是否继续发布？"
   - 任何一项fail → 自动修复或报告错误。

6. **强制检查点 (CheckPoint 5)**：
   - 等待用户回复"是/继续"。
   - （未来可选：完全自动化，跳过此确认）

## Step 6: 排版与发布 (Publishing)
**前提条件**：用户在 Step 5.5 回复"Continue"。

**动作（必须严格按顺序执行）**：
1. **转换 Markdown 为微信 HTML**：
   ```bash
   python3 skills/write-article/scripts/convert_to_wechat.py output/[article-slug]/[article-slug].md preview_app/articles/[article-slug].html
   ```

2. **更新文章列表**：
   ```bash
   python3 sync_articles.py
   ```

3. **输出预览链接**：
   ```
   ✅ 发布完成！预览地址：http://localhost:8000/preview_app/
   ```

4. **数据回填（闭环验证，2026-07 新增）**：
   - 提醒用户：**发布 48 小时后**，把该篇的 阅读/点赞/在看/转发 四个数记进自己的数据台账（一行一篇，含标题类型标签 🏷️/🙋/⚖️ 和时效级别）。**这一步是整套流程里唯一能反哺规则的环节**——积累十几篇之后，哪类标题、哪条车道在你的号上真正有效，就有依据了，届时回头改 `lanes/` 和 `rules/persona.md`。
   - 台账攒够 8~10 篇新规则文章后，做一次小复盘：新规则选题/标题的中位阅读 vs 旧文中位数 269——**规则是否有效由这张表说了算，不由感觉说了算**。发现规则没用就改规则。
